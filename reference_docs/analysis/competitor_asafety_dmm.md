# 竞品调研：天津飞安 ASafety《模拟机质量维护系统》(dmm)

来源：https://tj-asafety.ccar142.com/dmm/ ，使用真实测试账号(test100)登录后的实地功能调研（非官网营销页面，是一套正在被真实ATO——天津飞安——生产使用的系统，数据库中有877条定期维护记录、415条备件出入库记录等真实运行数据，参考价值高于Simorg/Hinfact的官网介绍页）。域名`ccar142`暗示其定位对标中国民航CCAR-142（对应本文档1.3节明确不做的FAA Part 142，但落地到中国监管语境下，说明"模拟机维护"这个子领域在国内已有成熟对标产品）。

与Simorg/Hinfact不同，这款系统**完全聚焦在"模拟机技术维护"这一个领域**（不含课程/学员/教员培训记录），但在这个领域里做得比本文档当前3.3/3.4节的设计更深、更贴近真实机务运行场景。以下按其左侧导航结构逐一记录。

## 整体导航结构（对应其9大一级模块）

用户管理 / 排班管理 / 工作记录 / 工单管理 / 故障中心 / 备件管理 / 设备管理 / 质量管理 / 统计报表 / 知识库 / 个人中心

## 1. 故障中心（对应本文档3.3.7缺陷处理，但明显更完整）

### 故障管理（故障列表）字段
- **故障编号**：DR1001形式的顺序编号（DR=Discrepancy Report，与航空维修术语一致）
- **故障描述**：中英双语
- **故障发生时间 / 最后更新时间 / 关闭时间**：三个独立时间戳，而不是我们目前只有reportedAt/correctedAt两个
- **历时天数**：自动计算的已开启天数（实测数据中有开启364天仍未关闭的案例——即长期挂账故障，对应下面的"故障保留单"机制）
- **故障保留单**：**"Ⅲ类(定期鉴定故障)"这类分级标签** —— 这是最有价值的发现：他们把故障按严重度/可保留性分成类别（类似真飞机MEL的Category体系），并附带保留理由文本（如"厂家回复，受真件影响无法做出修改，在不影响训练科目的前提下，申请保留"）。这比我们目前"MMI缺陷=完全阻断该科目训练"的二元判断更贴近真实机务实践：**有些缺陷经评估后可以带病运行，但需要正式的分级+理由+（隐含的）审批留痕**。
- **故障来源**：如"局方鉴定报告"——记录这个故障是怎么被发现的（周期性鉴定中发现 / 日常使用中发现 / QTG测试中发现等）
- **等级**：故障严重度等级（与"故障保留单"的类别是两个维度）
- **中断训练时间/hrs**：每条故障关联的培训中断小时数——**直接对应我们刚做完的FSTD Performance Metrics里"Lost training time"指标，说明这个指标的数据源头应该是逐条故障记录累加，而不是单独人工填报**
- **剩余天数**：类似倒计时的字段（我们的discrepancy有30天修复时限，这里"剩余天数"字段印证了这类倒计时确实是行业通用做法）
- **子系统**：故障归属的设备子系统分类——可以和我们FCS的14个特征(FcsCharacteristic)对应，作为legacy体系下的等效分类
- **软硬件**：Software/软件、Hardware/硬件、QTG/QTG问题——三分类，区分故障根因类型
- **责任组 / 责任人**：既有团队归属也有个人归属
- **屏蔽状态**："未屏蔽"——存在"屏蔽"某条故障（暂不重复提醒/暂不计入统计）的机制，需谨慎对待：合理用途是"已有对应保留单覆盖，避免重复告警"，但也可能被滥用为掩盖长期未修问题，如果借鉴需要配合审批留痕
- **AOG故障**：借用真飞机"Aircraft On Ground"术语，标记该故障是否导致设备停用级别
- **是否为模拟机故障**：区分"确实是设备问题"还是"操作/环境等其他原因导致的误报"，用于故障数据的质量过滤

### 故障审核（独立页面，与故障管理分开）
- 故障提交后进入**审核队列**，走"提交→审核"两阶段流程，审核环节支持附件。这是一个独立于故障处理本身的**质量把关环节**，与我们的合规监督(finding→corrective action)模式类似，但专门针对故障报告本身的真实性/完整性做二次确认，值得在3.3.7里补充"故障报告审核"这一步。

## 2. 排班管理 / 停飞管理（本文档目前没有对应概念）

**停飞管理**是一个日历式界面：按月选择日期，勾选某台设备在某天"停飞"（停用）。备注写明："标记后该模拟机将不再生成航前航后检查单，已生成的单子将取消"。

这说明两件事：
1. **设备停用应该是一个带时间范围的日历标记，而不只是我们`Fstd.status`那样的单一当前状态字段**——过去/未来的停用历史也需要可查。
2. **停用状态应该联动抑制该设备的常规检查单生成**——避免设备明明停飞、系统却还在提醒"今天的航前检查还没做"这种噪音告警。这是一个很实用的细节，值得吸收进3.3.6变更管理里的Deactivation处理逻辑。

设备清单也顺带证实了这家机构除固定翼/旋翼全动模拟机（737MAX1/2、A320、B737NG、EC135）外，还管理**动态舱、服务舱、水舱、火舱、舱门**等专项训练设备（客舱应急设备训练器材），这类设备虽不在CS-FSTD范围内，但同样纳入了这套维护管理系统——提示我们"设备管理"模块的外延可以不局限于严格意义的FSTD。

## 3. 工作记录 → 定期维护（本文档目前完全没有的模块）

这是一个**独立于QTG年度鉴定、独立于ORA.FSTD周期性评估**的内部常规维护体系，分**周检/月检/半年检/年检**四个层级，每条记录含：
- 任务日期、模拟机、执行人、责任人（可多人）
- 检查时间、最后更新人/更新时间
- **审核状态**（未审核/通过）+ 审核人——同样是"执行→审核签署"两阶段
- 任务状态（已完成）

实测数据877条，说明这是这家机构**用得最频繁的功能之一**。这正好对应本文档3.2.6提到的"AMC1 ORA.FSTD.105(a)(1) 应建立常规维护排期"，但我们目前只字带过、没有落地成模块。**这是本次调研发现的最值得补进3.3节的空白项**：一套多层级(周/月/半年/年)、可配置检查单、执行+审核两段式的常规维护任务模块，与QTG周期性运行（3.3.4，按季度）、周期性评估（3.3.5，按年/三年）是三套并行但各自独立的周期性机制，服务于不同的合规/运维目的。

工作记录下还有：**航前记录/航后记录**（对应我们已吸收的FAA §60.19 24小时功能预检，但他们分成"航前"和"航后"两条独立记录，而不是一条）、**QTG管理/QTG设置**（设置=QTG测试项的模板配置，管理=实际执行记录，模板与执行分离）、**升级校准**、**过渡支持记录**（含义待确认，可能是设备升级/改装期间的过渡期支持记录）、**检查单配置**——一个**通用检查单模板配置引擎**，而不是像我们现在FstdSafetyFacilityCheck那样把检查项硬编码在前端常量里。

## 4. 工单管理（本文档目前没有对应的通用任务框架）

工单号格式如`NON20260918002`（NON=非例行/Non-routine，隐含还有"例行工单"类型）。字段：
- 工单类型（非例行工单）、工单名称
- 可选关联**备件名称/件号PN**——工单可以直接指向"需要用到某个备件"
- 项目组、工单生成日期/任务截至日期/工单完成日期
- **稽催日期**——一个专门的"催办"日期字段，与截至日期分开
- 任务提要、**任务责任人（可多人）**、任务进度

这本质上是一个**跨模块的轻量任务/行动项管理框架**，实际用途包括"联系厂家提供操作步骤""统计未解决的鉴定遗留问题并询价"这类不严格属于"故障"但需要跟踪到底的行政/技术协调任务。**对我们的启示**：本文档目前把"行动项"分散建在好几个不同模型里（CorrectiveAction纠正措施、MitigationAction缓解措施、SafetyReviewBoardAction安全评审行动项），字段各不统一。如果后续要加一个通用工单/任务框架，可以参考这里"截止日期+催办日期+可多责任人+进度状态"的字段设计，甚至考虑让上述几个分散的Action模型未来收敛到同一套任务框架上。

## 5. 备件管理（对应本文档3.4，是本次调研发现差距最大的模块）

左侧导航下细分11个子页面，我们目前3.4节的设计（SparePart/PartMovement/Tool/Supplier/PurchaseOrder四张表）明显是简化版。逐项对照：

| 子页面 | 我们现状 | 差距 |
|---|---|---|
| 备件清单 | 有(SparePart) | — |
| 入库申请 | 无 | 入库需要走"申请"流程，而不是直接建记录 |
| **备件记录**（出库/入库/拆下件/借用件/新构件/盘点，6个子tab） | 只有单一PartMovementType枚举 | 见下方详细拆解 |
| 备件需求 | 无 | 正式采购前的"需求登记"，区别于采购单——一种预测/申请阶段的轻量记录 |
| **故障件管理** | 无 | 从设备上拆下来确认为故障的部件，单独进入送修/退换流程跟踪，不等同于普通"入库/出库" |
| **报废管理** | 无 | 备件报废需要走审批流程，不是简单减库存 |
| **检测管理** | 无（我们只有Tool的校准） | 备件本身（不只是工具）的入库检测/定期检测记录 |
| 采购管理 | 有(PurchaseOrder)但更简单 | — |
| 工具管理 | 有(Tool) | — |
| 拆下件记录 | 无独立概念 | 从设备拆下但未必是故障件（如为了临时借用给其他设备），与"故障件管理"是两个概念 |
| 备件信息配置 | 硬编码枚举 | 备件类型/资产类型等主数据应做成可配置字典，而不是写死在代码里 |

**备件出库记录的字段清单**（最完整的一张表，逐条列出是因为信息量很大）：
序号、备件名称、件号PN、单据号、**序列号**、**关联故障号**、**备件类型**（消耗件/周转件）、**资产类型**（乘务/耗材/原材料/固定资产/油脂等）、固定资产编码、型号、**使用模拟机**、出库时间、**出库用途**（使用/借出）、出库数量、出库单价、出库金额、**库房**（含"天津飞安库房"和"天津飞安库房2（托管库）"两个仓库，后者是寄售/托管库房）、**备件使用位置**（设备上的具体分区，如"Q2-2""重货区"）、备件存放位置、领用人、出库人、备注（中英双语）、操作："关联DR修改"。

从这张表能提炼出五个本文档目前完全没有建模的关键概念：

1. **周转件(rotable) vs 消耗件(consumable) 分类**：这是航空维修最基础的备件分类之一——周转件是可维修、有序列号、全生命周期跟踪、送修后可复用的部件（如伺服阀），消耗件是用完即弃、不跟踪序列号的耗材。我们的SparePart模型目前没有这个区分，导致无法支持周转件的"拆下→送修→测试→复装"完整生命周期跟踪。
2. **关联故障号（DR号）**：每条备件领用记录直接关联到触发这次领用的具体故障/缺陷编号，形成"缺陷→领用备件→（隐含地）关闭缺陷"的完整追溯链。这个link目前我们的PartMovement和DiscrepancyLog之间是断开的。
3. **多库房 + 寄售/托管库房**：不是单一库存数字，而是"按仓库分别记录库存"，且明确支持第三方托管库房这种特殊库存类型。
4. **使用位置 vs 存放位置**：存放位置是仓库货架编号，使用位置是这个备件最终安装到了设备的哪个分区/工位——两者是不同维度的位置信息。
5. **借出（而非领用消耗）作为出库用途之一**：呼应"借用件记录"这个独立tab——备件/整机部件的对外借出是一种正式的、需要跟踪归还的库存动作，不同于普通领用消耗。

## 6. 质量管理 / 统计报表 / 知识库 / 个人中心

> **2026-10-02 起已二次深入调研**：由用户在内置浏览器中登录真实测试账号后（角色"维护工程师"），**只读浏览，未保存/提交/删除任何数据**，逐页走了排班管理、工作记录、质量管理、统计报表、知识库、备件各页签。逐页实测记录见下方 6.1–6.9；紧随其后的"6.0 早期概览"是首次调研时的简要笔记，保留以便对照。本系统由此转化出的需求见需求清单 3.12，实施顺序见其第4节"第四期"。
> 该系统的测试账号在2026年9月没有训练计划数据，所以"计划块的外观"无法实测，只确认了网格结构和配置项。

### 6.0 早期概览（首次调研）

- **质量管理**下有：问卷管理、培训管理、会议记录、其他检查——"会议记录"很可能对应我们已实现的安全评审委员会会议，但这里是作为质量模块的通用子功能，不局限于安全评审。
- **统计报表**：任务统计、**故障统计**、**PM统计**（对应上面的定期维护）、**备件统计**、维护工时统计、**运行效率统计**——"运行效率统计"很可能就是可用率/可靠率一类指标，印证了我们刚做的FSTD Performance Metrics方向是对的，是行业通用需求而非我们过度设计。
- **知识库**：原厂技术手册、管理规范、培训资料、外部文件、文件查询——一个**通用的文档库/知识库模块**，本文档目前完全没有对应设计（QTG文件上传只是单点功能，不是通用文档库）。
- **个人中心**：含"资质管理"——**让员工自己就能查看本人的资质到期情况**，是人员资质到期提醒(3.5)的一个自助查询UX补充，不需要都通过管理员后台查看。
- 顶栏还有一个带**未读数角标的消息通知中心**（🔔图标+红色数字），本文档3.9提到的各类"到期提醒/超期告警"目前在我们系统里都是页面加载时临时计算展示，没有沉淀成一个持久化的消息/通知中心。

### 6.1 排班管理（`/workforce/*`）

- **维护排班**：筛选"选择日期（月）/项目组/班次"；顶部是班次色块图例（M/E/D/B/S/…，可左右滚动）；主体是"姓名 × 日"月度网格，列含姓名、排序（拖动手柄）、班组；按钮：修改历史、批量取消、顺延、导入、导出、保存。首页另有"我的排班表"（约15天窗口）。班次说明：M白班 08:30–17:00，E晚班 17:00–次日08:30，D 24小时班 08:30–次日08:30，B出差，S病假，V倒休，Q其他，A年假。
- **班次配置**（基础配置→班次）字段：名称、代码、开始时间、结束时间、班次属性、项目组、**是否生成维护任务**、休息时长、描述。
- **定期排班**：筛选日期（月）/项目组；图例周检/月检/半年检/年检 + "自定义"；行是设备（EC135、B737NG、A320、737MAX1、737MAX2，以及舱门、水舱、火舱、动态舱、服务舱）；按钮：查询历史数据、保存、批量取消、导入导出、历史排班。
- **停飞管理**：按月日历，行是设备；按钮"设置班次/停飞/取消停飞/导入"；页面备注原文："点击/选中相应时间点，标记模拟机停飞；当天及之后的日期都可标记，标记后该模拟机将不再生成航前航后检查单，已生成的单子将取消。"
- **训练计划**：两个页签。"总计划"= 单日网格，列是设备，行是2小时刻度（02:00…次日02:00），可按教员名称查询，日期左右切换；"设备计划"= 先"设备选择"，再整月逐日，可导出。两处都有"客户配置"按钮，弹窗字段：序号、客户名称、配色（另有操作列）；示例客户：多客户、个人训练（奥凯）、湖北国际货运、联航、航科院。
- **工时统计**：筛选"统计周期/项目组"；表头：序号、项目组、名称、班次（小时）{晚班、白班、加班时长}、统计工时；可导出。样例：夜班人员当日 16 小时。

### 6.2 工作记录（`/workRecord/*`）

- **任务总览**：按日期范围查询，另有明细页。
- **值班日志**（页签：值班日志 / 交接班查询）：筛选值班日期、状态、项目组、填写状态、执行人、设备、关键词；"非常规任务/常规任务"按钮；新增、全部导出、批量下载、批量打印。新增表单：值班信息（DATE、SHIFT、TEAM NO.、Engineers + 添加人员）→ 交接工作（来自上一个班次）→ DR 操作记录 → 值班内容（添加记录）→ 交接工作（交接给下个班次，默认转下一班次，可"指定交接班次"）。
- **巡检记录**（当日记录/历史记录）：筛选项目组、巡检区域；另有总表（overall record sheet）。
- **航前记录 / 航后记录**：筛选设备、状态、填写状态、执行人（航后另有值班日期）；新增、导出、批量下载/打印。
- **定期维护**（周检/月检/半年检/年检四个页签）：筛选定检日期、设备、审核状态；新增、导出、批量打印/下载。
- **QTG 管理**：QTG 信息及对比页；**QTG 设置**两个页签：时段设置、责任人设置。

## 对系统设计的启示（汇总）

这款系统证明"模拟机技术维护"本身可以独立支撑起一整套相当复杂的系统，比本文档3.3/3.4两节目前的设计厚重得多。最值得优先吸收的三点，按价值排序：

1. **故障/缺陷处理需要分级保留机制**：不是简单的"开启/已纠正"二元状态，而是要有类似MEL的保留类别+理由+审核签署，这样"长期已知、评估后可接受"的缺陷可以被正式记录而不是死等修复或者被忽略。
2. **备件管理需要"周转件全生命周期跟踪"+"与故障单直接关联"**：这两点结合起来才能支撑起"因为DR1001需要更换伺服阀→领用周转件→旧件拆下确认故障→送修→测试合格→入库待用"这样一条完整的机务闭环，目前我们的Inventory模块只覆盖了这条链路里最简单的"领用/入库"两端。
3. **常规维护(PM)应该是独立于QTG和周期性评估的第三套周期性机制**：按周/月/半年/年多层级、执行+审核两段式，这填补了本文档3.2.6提到但未落地的"日常维护排期"空白。

这三点加上停飞日历、工单/任务框架、通知中心、知识库，是这次调研里认为值得排进后续迭代的候选项，已在正文3.3/3.4节及第4节分期计划中补充标注。
